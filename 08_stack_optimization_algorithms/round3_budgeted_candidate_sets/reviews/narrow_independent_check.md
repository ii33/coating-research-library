# 二维候选集合：窄独立核查

## 范围与结论

核查对象限于 `models/candidate_sets.py`、`data/candidate_contract.json`、复制的 `dependencies/t07r3/data/case.json` 与继承光学/区间实现。没有重跑 tiny；独立光学检查共调用 16 次单波长区间核（4 个点 × M0 三节点和 M1 一节点），其后所有反例/预算检查均为纯有理或不触发光学。没有 browser/headless、设备、heavy 或 quota 绕过。

结论：二维坐标、单位、层序和同一样品共享 z 的编码一致；精确分割覆盖和预算耗尽时 UNKNOWN 的行为符合声明；目标下界包含 UNKNOWN，目标剪枝只做优化标注；当前版本要求本进程内 `screen`/`validate_point` 生成并登记证明记录，再允许优化上界/下界运算。两类未可信输入风险先由我在旧版本代码阅读中发现，随后父任务已加输入 provenance 和重算保护；修复后的纯有理负例都被拒绝。此核查不是全局或物理证书，也不是 DeepSeek/Seed/Sol 正式审查链。实际模型为 GPT-6 Luna；formal 链仍 pending。

## 编码、量纲与同样品映射

合同是二维 (z, v6)：`z=h/h_ref` 无量纲，`h_ref=3.3893682215916026e-10 m`；厚度按 `d_i_um=(d_legacy_nm/1000)*z*(v6 if i==6 else 1)`。被继承的正厚度来源门给出 `Z=[1191827825890425099974357/1208925819614629174706176, 306505953334708322791479/302231454903657293676544]`，约 `[0.9858568710777851, 1.014143128922215]`，对应来源厚度约 `[3.341431949868774e-10, 3.437304493314431e-10] m`。这只是正厚度 outer envelope；它不证明 Z 中任一点是由实际 Q/ρ/留存联合来源实现的。

配方表按 substrate-to-incident 编号；光学 evaluator 反转为 incident-to-substrate `[6,5,4,3,2,1]`。因此原始 layer 6 是入射侧最外层 YF3（n=1.5，名义 1982.05 nm），只有它乘 v6，其它五层只乘同一个 z。`channel_interval` 对 M0、M1 都使用同一个 `(z,v6)` box；每个候选独立存在自己的 z，没把不同候选或批次误设为共享 latent。

两个通道是合成离散反射算子：M0 在 4.25、4.26、4.27 μm 以 1/4、1/2、1/4 加权；M1 为 10 μm 单点、权重 1；各自硬误差为 ±0.001 R。材料为显式常数 n、k=0、半无限基底模型；这些不是实测光学常数，也不构成连续波段/实物结论。

## 覆盖、预算与目标界

- 独立构造的精确二维树通过 `verify_cover`；删除一个子叶得到 `coverage_hole`。当前代码还在 `screen` 结束时登记核心记录指纹，`optimize_bounds` 再验指纹、覆盖、合同及每叶 J/g 的精确值。伪造/改写 run 无法仅靠 JSON 字段自证。
- 最终代码下零节点预算产生 1 个全域 UNKNOWN、0 个 OUT、0 次区间调用，覆盖仍成立；节点可用但区间预算为 0 时，原因是 `interval_budget`，同样 1 UNKNOWN、0 OUT、0 次区间调用。两者都没把预算耗尽转换成观测 OUT。
- 最终代码下的窄盒 `z=1, v∈[0.9,0.91]` 在零节点预算时仍作为 UNKNOWN 参与优化下界：精确下界 `1184747303222336591212021/151115727451828646838272`，约 7.84；UNKNOWN 计数为 1。全域零预算盒跨过目标 v=1.05，下界为 0。可行约束仅在区间证明 `g=z*v-1.03>0` 时排除；目标界从未改写 data_class。
- `validate_point` 用区间预测对每个选定通道给出 IN/constraint 检查，只有其合成代理可行点能成为上界见证。旧版代码曾直接信任调用者给出的 `proxy_feasible` 和 `objective_exact`；另曾未核验任意传入的 run 对象。两点是代码检查中发现的风险，并未宣称已在旧版成功跑完利用样例。现在 `validate_point`/`screen` 在当前进程登记 canonical digest，三合同绑定；`optimize_bounds` 校验登记、覆盖，并重算目标/约束区间。直接篡改见证/记录或跨进程加载未重放的见证均失败。若要用保存 JSON 再调用此 API，须在新进程内重新 screen / validate_point 并支付预算；保存 JSON 本身不是 API 可信凭证。
- 优化剪枝是 `PRUNED_OBJECTIVE_BOUND` 注释，不改变观测类；`global_optimizer_certificate` 与 `physical_optimum_certificate` 仍为 false。OUT 是观测区间不相交的覆盖证据，不能由优化器未找到、算术失败或预算耗尽产生。
